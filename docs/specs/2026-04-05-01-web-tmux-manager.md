# BeeBaby Admin — Web tmux Manager

## Problem Statement

Managing tmux sessions via CLI commands is friction-heavy: remembering `tmux ls`, `tmux attach -t`, `tmux new -s`, `tmux kill-session -t`, prefix keys for session switching, etc. When SSHing into beebaby from different devices over Tailscale, there's no visual overview of what's running or easy way to jump between sessions.

## Solution

A self-hosted web app at `beebaby:8001` that provides a browser-based tmux session manager. The app gives a persistent dashboard with a sidebar listing all tmux sessions, a top bar for status/controls, and a main area rendering 1–4 live terminal panes connected to tmux sessions. No authentication — the Tailscale VPN handles access control.

## User Stories

1. As a user, I want to see all active tmux sessions in a sidebar so I can quickly understand what's running on beebaby.
2. As a user, I want to click a session to attach to it in a terminal pane so I don't need to remember tmux attach commands.
3. As a user, I want to create a new tmux session from the UI with an optional name so I can start work without a separate SSH terminal.
4. As a user, I want to rename a tmux session from the UI so I can organize my sessions meaningfully.
5. As a user, I want to kill a tmux session from the UI so I can clean up without remembering the command.
6. As a user, I want to view 1 terminal pane at full width/height for focused work.
7. As a user, I want to split into 2 panes (vertical split) so I can watch two sessions side by side.
8. As a user, I want to split into 4 panes (2x2 grid) so I can monitor multiple sessions simultaneously.
9. As a user, I want terminal panes to remain connected when I navigate away and come back so sessions persist across browser refreshes.
10. As a user, I want to detach a pane from its session without killing the session so I can free up a pane slot.
11. As a user, I want the sidebar to auto-refresh so I see new/killed sessions without manual refresh.
12. As a user, I want to resize terminal panes and have xterm.js reflow text correctly.
13. As a user, I want keyboard input, colors, scrollback, and cursor behavior to work like a real terminal.
14. As a user, I want the app to be accessible from any device on my Tailscale network (laptop, phone, tablet).
15. As a user, I want the app to run as a systemd service so it starts on boot and restarts on crash.

## Data Flow

1. **Browser loads app** → Express serves the React SPA (Vite-built static assets in production).
2. **Sidebar populates** → React calls a REST endpoint that shells out to `tmux list-sessions` and returns structured session data (name, window count, created time, attached status).
3. **User attaches to session** → React opens a WebSocket connection to the server. Server spawns a `node-pty` pseudoterminal running `tmux attach -t <session>`. Bidirectional data flows: keystrokes from xterm.js → WebSocket → node-pty → tmux, and tmux output → node-pty → WebSocket → xterm.js.
4. **User creates/renames/kills session** → React calls REST endpoints that shell out to the corresponding `tmux` commands. Sidebar refreshes via polling or push.
5. **Pane layout changes** → Purely client-side. React manages a layout state (1, 2, or 4 panes) and each pane independently holds a WebSocket connection to a tmux session (or is empty/unattached).
6. **User disconnects** → WebSocket closes, server kills the node-pty process. The tmux session itself continues running (tmux is independent of the PTY attachment).

## Behavior

- **Session list**: Refreshes on a short interval (polling every 2-3 seconds). Shows session name, number of windows, whether currently attached (by this app or elsewhere), creation time.
- **Pane layout**: Default is 1 pane. User can switch between 1x, 2x (vertical split), 4x (2x2 grid). Layout preference could be persisted in localStorage.
- **Empty panes**: When layout has more panes than attached sessions, empty panes show a prompt to select a session.
- **Session creation**: Default name is auto-generated by tmux (incrementing numbers). User can optionally provide a name.
- **Kill confirmation**: Killing a session should require confirmation (it's destructive).
- **Terminal rendering**: xterm.js handles all terminal emulation — colors (256 + truecolor), unicode, mouse events, scrollback buffer. The server just passes bytes.
- **Resize handling**: When browser/pane resizes, xterm.js reports new dimensions → sent over WebSocket → node-pty resizes PTY → tmux reflows.
- **Multiple browser tabs**: Each tab gets independent WebSocket connections. Multiple tabs can attach to the same tmux session (tmux supports this natively).
- **Top bar**: Minimal — app name/logo, layout toggle buttons (1/2/4 panes), possibly connection status indicator.

### Responsibilities

- **Server owns**: PTY lifecycle, tmux command execution, WebSocket management, serving static assets.
- **Server hides**: node-pty details, shell command construction, PTY file descriptors.
- **Server exposes**: REST API for session CRUD, WebSocket endpoint for terminal I/O.
- **Client owns**: Pane layout, xterm.js instances, session-to-pane assignment, UI state.
- **Client hides**: xterm.js rendering internals, WebSocket reconnection logic.
- **Client exposes**: Session dashboard, terminal panes, layout controls.

## Modules

- **Terminal Server (WebSocket handler)**: Manages WebSocket connections, spawns node-pty processes attached to tmux sessions, handles bidirectional data relay and PTY resize.
  - Role: **defines** the WebSocket protocol (message types for data, resize, attach, detach)
  - Interface: `ws://host:8001/ws/terminal?session=<name>` — binary frames for terminal I/O, JSON frames for control messages (resize, error)
  - Test: yes

- **Session API (REST endpoints)**: CRUD operations on tmux sessions — list, create, rename, kill. Thin wrapper around tmux CLI commands with structured JSON responses.
  - Role: **defines** the REST API contract
  - Interface: `GET /api/sessions`, `POST /api/sessions`, `PATCH /api/sessions/:name`, `DELETE /api/sessions/:name`
  - Test: yes

- **Terminal Pane (React component)**: Wraps xterm.js instance, manages WebSocket connection lifecycle, handles resize events. One instance per visible pane.
  - Role: **consumes** WebSocket protocol from Terminal Server
  - Interface: Props — session name (or null for empty pane), pane dimensions
  - Test: no (xterm.js is a visual component, smoke-test manually)

- **Pane Layout Manager (React component)**: Manages the 1/2/4 pane grid layout, assigns sessions to panes, handles layout switching.
  - Role: **consumes** session list from Session API
  - Interface: Layout state (1, 2, 4), pane-to-session mapping
  - Test: no (UI layout, smoke-test manually)

- **Session Sidebar (React component)**: Displays session list, provides create/rename/kill controls, click-to-attach.
  - Role: **consumes** Session API
  - Interface: Session list data, callbacks for CRUD actions and pane attachment
  - Test: no (UI component, smoke-test manually)

## Resolved Decisions

- **Tech stack: Node.js + Express + React + Vite + xterm.js + node-pty** — Node is already installed on beebaby, xterm.js + node-pty is the canonical pairing (used by VS Code), React + Vite for a modern frontend with fast dev iteration.
- **No authentication** — Tailscale VPN provides network-level access control. Adding auth would be redundant friction for a single-user setup.
- **Split panes, not tabs** — User wants to see multiple sessions simultaneously. 1x (full), 2x (vertical split), 4x (2x2 grid).
- **Sidebar + top bar layout** — Session list lives in a persistent sidebar. Top bar for layout controls and status. Main area is the pane grid.
- **Systemd user service for deployment** — Matches existing pattern on beebaby (hiking-food.service). User-level service, auto-restart, starts on boot.
- **Vite builds static assets, Express serves them in prod** — Single process, single port. No separate frontend server in production. Dev mode uses Vite dev server with proxy to Express.
- **No bespoke system management features** — tmux sessions provide full shell access; any system management can be done from a terminal.
- **Flow control from the start** — watermark-based PAUSE/RESUME in the WebSocket protocol. ~35 lines total across client and server, prevents OOM on high-throughput output (`cat bigfile`). Easier to include in the initial protocol design than retrofit.
- **tmux window-size policy: `latest`** — session tracks the most recently active client. User rarely attaches multiple panes to the same session; `latest` gives no dead space and acceptable reflow behavior for single-user use.

## Testing Decisions

- **Terminal Server**: Integration tests — verify WebSocket connection lifecycle, data relay to/from a real tmux session, resize messages.
- **Session API**: Integration tests — verify CRUD against real tmux (create session, list it, rename it, kill it). Fast and deterministic since tmux is local.
- **Frontend**: Manual smoke testing only. No component tests for terminal panes or layout — the value is in the visual/interactive behavior which automated tests wouldn't meaningfully cover.
- **Agent-browser screenshots**: Can be used for visual regression of the dashboard layout if desired later.

## Out of Scope

- Authentication/authorization (VPN handles it)
- File browser or file upload/download
- Session sharing between multiple users
- Recording/playback of terminal sessions
- Mobile-optimized layout (functional on mobile via Tailscale, but no special mobile UI)
- Notifications or alerts
- Custom theming (use xterm.js defaults, can be added later)
